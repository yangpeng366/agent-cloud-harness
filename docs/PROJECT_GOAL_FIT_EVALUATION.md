# PROJECT_GOAL_FIT_EVALUATION

## 1. 目的

本文档用于评估 `agent-cloud-harness` 当前是否满足以下项目目标，以及距离该目标还有多远：

> 让强模型调度小模型，在长周期任务中持续协作，以更低成本完成更大的任务，并提升小模型的能力表现。

这里的重点不是讨论愿景是否成立，而是评估：

1. 当前项目设计是否**方向上匹配**这个目标
2. 当前能力是否已经**部分满足**这个目标
3. 距离真正满足还缺哪些关键能力、证据和评测
4. 下一步应如何把“概念正确”变成“结果成立”

---

## 2. 结论摘要

### 2.1 总体结论

当前判断：**方向上明确匹配，机制上部分满足，结果上尚未被充分证明。**

更直接地说：

- `agent-cloud-harness` 当前的架构方向，**适合支撑**“强模型调度小模型完成长周期任务”这个目标
- 现有强调的 continuity、checkpoint、handoff、resume、audit 等能力，**正是这个目标所需的核心控制层能力**
- 但从现有文档与评测设计来看，项目目前更接近：
  - **已经证明了问题意识和系统设计方向是对的**
  - **尚未充分证明它真的提升了小模型表现，或真的降低了大任务成本**

所以当前最准确的评价不是“已经满足”，而是：

> **具备成为该目标实现底座的架构条件，但尚未完成面向该目标的闭环验证。**

### 2.2 一句话判断

如果把目标拆成两部分：

1. **让长周期任务可持续执行**
2. **让强模型调小模型后，整体效果优于常规方式**

那么当前项目：

- 对第 1 部分，**匹配度较高**
- 对第 2 部分，**理论成立，但证据还不够**

---

## 3. 为什么说项目方向是匹配的

结合现有文档 `AGENT_EVAL_AND_REFERENCES.md`、`EVAL_SCENARIOS.md`、`GO_TO_MARKET_AND_PRODUCTIZATION_PLAN.md`，当前项目至少在以下几个层面与目标一致。

### 3.1 项目关注的是控制层，而不是单轮模型输出

目标里最关键的一点不是“找个更强模型”，而是：

- 让不同能力层级的模型形成分工
- 让系统可以跨多轮、多阶段执行
- 让大模型承担高价值决策，小模型承担低成本执行

而 `agent-cloud-harness` 当前的设计重点正是：

- routing
- checkpoint
- handoff
- pause / resume
- human gate
- judgment
- audit trace

这说明项目瞄准的是**控制平面**，而不是某一个模型本身。

这与目标高度一致，因为“强模型调小模型”的前提本来就是：

> 需要一个能稳定做任务拆解、状态维护、执行交接、恢复和验收的控制层。

### 3.2 项目已经抓住了长周期任务的真正瓶颈

目标强调的是“大的长时期任务”。

而现有评测文档已经明确指出，长任务的关键问题不是单次回答，而是：

- continuity
- state consistency
- recoverability
- handoff quality
- human boundary correctness
- auditability

这说明项目没有把问题理解成“多模型聊天”，而是理解成：

> 如何让任务在中断、切换、恢复、交接后仍然可持续推进。

如果没有这层能力，再聪明的模型也很难稳定完成长期任务。

因此，项目对问题的理解是对的。

### 3.3 现有评测思路已经接近“系统级能力验证”

从 `EVAL_SCENARIOS.md` 看，项目当前已经准备评测：

- pause / resume
- handoff
- escalate
- judgment
- trace replay
- multi-checkpoint continuity

这说明项目不是在用“主观感觉很聪明”来评价自己，而是在尝试验证：

- 是否能恢复
- 是否能路由
- 是否能交接
- 是否能保持状态一致

这对“强模型调小模型”的目标尤其重要。

因为当多个模型协作时，真正决定结果的通常不是单次输出质量，而是：

- 分工是否合理
- 切换是否正确
- 状态是否保真
- 是否能纠偏

这些都必须靠系统级评测来证明，而当前项目已经在往这个方向走。

---

## 4. 为什么说当前只是“部分满足”

虽然方向匹配，但如果严格按目标来判断，当前项目还不能说已经满足，因为还有几个关键层面没有被真正证明。

### 4.1 尚未证明“强模型调度小模型”真的成立

现有文档里已经有了这个主叙事，但从证据看，仍然主要停留在：

- 产品定位层
- 架构合理性层
- 测试设计层

还没有看到充分的闭环证据证明：

- 强模型是否真的在做 planner / router / evaluator / recovery
- 小模型是否真的承担了可分解执行
- 二者协作后是否优于单独用强模型或单独用小模型

也就是说，目前项目**支持这个命题**，但还没有**验证这个命题**。

### 4.2 尚未证明“小模型能力表现被提升”

这是目标里最难的一部分，也是最容易被说得太早的一部分。

“提升小模型的能力表现”不能只靠感觉，至少要证明下面几件事中的一部分：

- 在 harness 中，小模型完成率高于裸跑
- 在 harness 中，小模型在长链任务里更不容易漂移
- 在 harness 中，小模型更少丢上下文
- 在 harness 中，小模型出错后能被纠偏并继续完成

如果没有这些对比证据，那么目前最多只能说：

> 项目有望放大小模型的有效表现。

还不能说已经做到了。

### 4.3 尚未证明“更低成本完成更大的任务”

这是另一个需要谨慎的点。

从产品逻辑上，这条路完全合理：

- 大模型只用在关键判断点
- 小模型承担大量执行
- 从而降低总成本

但要让这件事成立，至少要有简单对比：

- 全程大模型直跑
- 全程小模型直跑
- 强模型调度小模型

比较它们在以下维度上的结果：

- 成功率
- 成本
- 时长
- 人工介入次数
- 恢复稳定性

如果没有这组对比，那么当前“低成本完成更大任务”仍然是一个合理假设，而不是已被证明的结果。

### 4.4 当前评测更强于 continuity，弱于 cost / capability amplification

现有文档的强项是：

- continuity
- routing correctness
- state consistency
- handoff
- human boundary
- auditability

这说明系统底座思路是扎实的。

但相对缺少的是面向目标本身的评测维度：

- 大模型调度是否带来更优 worker 选择
- 小模型在 harness 内是否比裸跑更好
- 多模型协作是否比单模型更划算
- 长任务规模放大后，系统优势是否更明显

而且最近的真实运行证据已经把问题进一步收窄了：

- harness 已经能够支持真实长任务中的代码/文档/文件证据收集
- tool-aware 多步执行、failure recovery、auto continue 也已经不是空白
- 当前更核心的瓶颈不是“完全不会推进”，而是“推进到一半后，何时继续、何时收成最终结果、何时明确停到 human gate”这条收口合同仍不够硬

也就是说，当前评测更像在证明：

> 这个 harness 是个靠谱的 continuity 控制层

而不是在证明：

> 这个 harness 已经让强模型调小模型的方案在任务效果和成本上跑通。

## 5. 分目标评估

为了更准确，建议把总目标拆成 4 个子目标来评估。

## 5.1 子目标 A：支持长周期任务连续执行

### 评价

**当前满足度：较高（设计层面），中等（结果层面）**

### 依据

项目已经明确关注：

- checkpoint
- pause / resume
- handoff
- trace
- state consistency

这说明体系结构对长任务连续性有较好的覆盖。

但从真实运行情况看，当前最薄弱的一层已经不是 continuity object 本身，而是 long-task closure：

- 任务中途失败后，是否会明确 `retry / handoff / waiting_human`
- 多轮推进后，是否能自然收成可信 `task_result`
- 中间轮已有局部产物时，是否会被误判成最终完成

### 当前判断

- 从设计上看，这部分是当前项目最强的部分
- 从文档上看，已经具备比较清晰的评测思路
- 从结果上看，还需要实际跑通 demo 和场景集来证明稳定性

### 结论

这是当前最接近“已经能做”的能力。

---

## 5.2 子目标 B：让强模型有效调度小模型

### 评价

**当前满足度：中等偏低**

### 依据

项目已经在叙事上明确：

- 强模型负责规划、路由、验收、纠偏
- 小模型负责可分解执行

但从现有材料看，相关部分还更多停留在目标描述与 demo 设想，而不是已经验证的系统行为。

### 当前缺口

缺少明确证明：

- 何时由强模型做决策
- 强模型如何选择小模型
- 调度规则和调度质量如何评估
- 调度失误后如何纠偏

### 结论

当前属于“目标方向已定，但尚未形成证据闭环”。

---

## 5.3 子目标 C：提升小模型能力表现

### 评价

**当前满足度：低**

### 原因

这是一个必须通过对比实验来证明的问题，而不是架构描述可以直接证明的问题。

### 必须回答的问题

- 同一任务中，小模型裸跑能做到什么程度？
- 在 harness 中被调度、补上下文、加 checkpoint 后，小模型能做到什么程度？
- 提升来自哪里？
  - 上下文压缩更好
  - 任务切分更合理
  - 纠偏机制更强
  - 验收后重试更有效

### 结论

当前可以提出假设，但不能声称已被证明。

---

## 5.4 子目标 D：以更低成本完成更大的任务

### 评价

**当前满足度：低到中等**

### 原因

产品逻辑成立，但缺少比较数据。

### 必须验证的内容

- 成本是否真的下降
- 总完成率是否没有因降成本而明显恶化
- 当任务规模变大时，系统优势是否增强
- 是否只是把复杂度转移到了调度层，而没有真正降低总成本

### 结论

当前更像“值得验证的核心商业假设”，而不是已成立事实。

---

## 6. 当前项目最强的部分

如果只看现在的项目基础，我认为最强的不是“模型分工”本身，而是以下几项。

### 6.1 continuity-first 视角是对的

很多 agent 项目先强调自主性、多 agent、工具调用数量，但你这个项目已经更早抓到了：

- 长任务真正难的是不中断
- 多模型真正难的是交接与恢复
- demo 之外真正难的是状态一致性和审计

这是非常重要的方向优势。

### 6.2 评测对象定义是对的

你当前不是在评估“模型是不是更聪明”，而是在评估：

- 系统是否可恢复
- 路由是否正确
- handoff 是否合理
- human gate 是否恰当

这说明你在评测的，是 scaffold / control plane，而这正是该项目最应该证明的东西。

### 6.3 项目已经具有成为“能力放大器”的基础

虽然还没证明小模型能力放大真的成立，但至少架构上已经有这个基础：

- 可路由
- 可拆分
- 可交接
- 可恢复
- 可验收

这些都是让小模型从“裸跑”变成“被组织起来工作”的必要前提。

---

## 7. 当前项目最明显的缺口

### 7.1 缺少面向“强模型调小模型”的专门评测

现有评测很强，但仍应新增一组专门问题：

- 调度质量是否提升
- 小模型表现是否提升
- 成本是否下降
- 大任务完成率是否提高

### 7.2 缺少 baseline 对比

没有 baseline，就很难证明“提升”。

至少需要以下三种基线：

1. 强模型单独完成任务
2. 小模型单独完成任务
3. 强模型调度小模型完成任务

然后比较：

- 成功率
- 成本
- 步数
- 恢复次数
- 人工介入次数

### 7.3 缺少面向“大任务、长任务”的固定 demo

当前有连续性场景，但还应该补一个更贴近目标的演示：

- 任务足够大，无法靠单轮轻松完成
- 至少跨多阶段
- 至少需要 2 个不同能力模型
- 至少发生一次 pause/resume 或 handoff

这样才能证明这不是普通的小任务 agent loop。

### 7.4 缺少“能力放大来自哪里”的解释链条

如果后面观察到小模型表现提升，还需要解释这提升来自哪里，否则容易被质疑只是偶然。

建议提前定义四类可能来源：

- 任务分解
- 上下文约束
- 结果验收
- 中断恢复与纠偏

后续评估时就能知道改进到底来自哪一层。

---

## 8. 建议新增的验证方案

如果要真正回答“项目是否满足该目标”，建议新增一组专门验证。

## 8.1 新增目标导向评测维度

在现有 continuity 评测之外，增加以下维度：

### G01. 调度收益

验证：

- 强模型做路由后，小模型选择是否优于固定路由
- 错误路由是否能被发现与修正

### G02. 小模型能力放大

验证：

- 小模型裸跑 vs harness 内执行
- 在长链任务上的完成率、漂移率、恢复后继续率

### G03. 成本收益

验证：

- 同任务下三种模式的 token / 调用成本比较
- 成本下降是否伴随质量或稳定性显著下降

### G04. 长任务规模收益

验证：

- 当任务长度和阶段数增加时，是否更能体现 harness 价值
- 系统优势是否在短任务不明显、长任务更明显

## 8.2 新增最小对比实验

推荐设计 3 组最小实验：

### 实验 A：单模型 vs 分层协作

任务：一个需要 3-5 个阶段的复杂任务

对比：

- 强模型单独做
- 小模型单独做
- 强模型调度小模型做

### 实验 B：裸跑小模型 vs 带 checkpoint/handoff 小模型

任务：一个中途必然中断的多步任务

对比：

- 不带 continuity 控制
- 带 continuity 控制

### 实验 C：长任务成本-效果曲线

任务：难度逐步上升的任务序列

观察：

- 难度上升后，哪种方式退化最快
- harness 是否能延缓小模型退化

---

## 9. 最终评估结论

如果严格回答“项目是否满足该目标”，我的结论是：

## 当前还不能说“已经满足”，但可以说“已经对准，并具备较强实现潜力”。

更细一点说：

### 已经满足的部分

- 对问题的理解基本正确
- 架构方向与目标高度匹配
- continuity / checkpoint / handoff / resume / audit 这些关键机制已经被识别出来
- 当前评测思路具备走向系统验证的基础

### 尚未满足的部分

- 尚未证明强模型调度小模型真的优于其他方案
- 尚未证明小模型能力表现被系统性提升
- 尚未证明大任务完成率与成本效率已经形成优势
- 尚未形成足够硬的 baseline 对比与结果证据

### 因此最准确的评价是

> `agent-cloud-harness` 当前已经像一个“面向该目标设计的控制层原型”，但还不是一个“已经证明该目标成立的系统”。

---

## 10. 推荐下一步

如果希望把这个结论从“方向成立”推进到“结果成立”，建议优先做三件事：

1. 新增一份目标导向评测文档，专门验证“强模型调度小模型”的收益
2. 固定一个长周期大任务 demo，至少包含：多阶段、handoff、resume、验收
3. 建立最小 baseline 对比：强模型直跑 / 小模型直跑 / 强模型调小模型

一旦这三件事补上，项目就能更有把握地回答：

- 是否真的让长任务更可做
- 是否真的让小模型更有用
- 是否真的让整体成本更合理

这会是从“好方向”走向“可证明价值”的关键一步。
